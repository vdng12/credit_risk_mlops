# Agent Sandboxes & uv Monorepos

Oct 26, 2026 · @Vi Dang
*Context: credit-risk-mlops repo*

---

## TL;DR

Give each agent its own **git worktree** on its own branch, and structure the Python code as a **uv monorepo** so any checkout can be brought up with one `uv sync` per component.

- **Worktree** = a second working directory sharing the same `.git` object store. The agent can trash its tree; your main checkout, index and build artifacts stay untouched. You review its branch and squash-merge or cherry-pick the good parts.
- **uv independent projects** = each component has its own `pyproject.toml`, `uv.lock` and `.venv`, so components can run divergent dependency stacks (e.g. the simulator's numpy 2 vs a serving component's torch 2.6).
- **Shared code** = a small library under `libs/` that consumers pull in through `[tool.uv.sources]` as an editable path dependency. Keep its dependencies minimal, and push heavy ones into extras.
- **Workspace** = the alternative when components should agree on versions: one `uv.lock` for the whole repo. Mixing both in one repo is fine.

## Git worktrees

A worktree is an extra checkout attached to the same repository: one object store, many working directories, each on a different branch.

```
credit-risk-mlops/        <- main worktree, on main
  .git/                   <- the real repo (objects, refs, config)
    worktrees/agent/      <- per-worktree HEAD + index
../credit-risk-agent/     <- linked worktree, on agent/feature-x
  .git                    <- a FILE: "gitdir: ../credit-risk-mlops/.git/worktrees/agent"
```

| Thing | Shared across worktrees | Per worktree |
|---|---|---|
| Objects (commits, blobs) | yes | |
| Branches, tags, refs | yes | |
| Config, stash, reflog | yes | |
| Working files | | yes |
| Index (staging area) | | yes |
| HEAD | | yes |
| Untracked files (.venv, .env, build/, output/) | | yes, and not copied |

A commit made in one worktree is visible from every other one immediately, with no fetch or push. One branch can be checked out in only one worktree at a time; use `--detach` to look at a commit without a branch.

**Why not just switch branches:** switching rewrites files in place, which invalidates build caches (painful for C++/Zig), forces a stash of WIP, and allows only one version running at a time. **Why not a second clone:** a clone duplicates the object store and needs fetch/push to sync.

```bash
git worktree add -b <new-branch> <path> [<start>]   # new branch
git worktree add <path> <existing-branch>
git worktree add --detach <path> <commit>
git worktree list
git worktree remove <path>          # --force if it has uncommitted changes
git worktree prune                  # forget worktrees whose dir you rm -rf'd
```

## Agent sandbox workflow

The agent goes wild on its own branch in its own directory, and nothing reaches `main` until you review it and merge.

### 1. Create the sandbox from current `main`

```bash
git worktree add -b agent/feature-x ../credit-risk-agent main
cd ../credit-risk-agent
uv sync --extra dev                  # workspace root: simulator + test deps
uv sync --project simulator          # standalone simulator venv (optional)
cp ../credit-risk-mlops/.env .env    # scoped/dummy creds, NOT your real .env
```

This project is a **uv workspace** with `members = ["simulator"]`. The root `uv sync` installs everything into one `.venv`. The simulator also has its own `pyproject.toml` for standalone use.

### 2. Run the agent

Point the agent to `../credit-risk-agent` as its working directory. Ask it to commit after each working step.

### 3. Review from your main worktree

No fetch needed — the branch already exists in the same object store:

```bash
git log --oneline main..agent/feature-x
git diff main...agent/feature-x                  # three dots: changes since branch point
git diff main...agent/feature-x -- simulator/    # scope to one component
git diff main...agent/feature-x -- tests/        # test changes only
```

### 4. Integrate what you keep

```bash
git merge --squash agent/feature-x && git commit    # take all as one commit
git cherry-pick <sha> <sha>                         # or only the good commits
git restore --source agent/feature-x -- path/to/file.py   # or single files
```

After merging, re-lock if the shared lib's deps changed:

```bash
uv lock --project simulator
uv sync --extra dev --locked
uv run pytest tests/ -q
```

### 5. Tear down

```bash
git worktree remove --force ../credit-risk-agent
git branch -D agent/feature-x
```

### Run parallel agents

One worktree and branch each (`agent/a`, `agent/b`), never two agents in one tree.

### Gotchas

- **Isolation is file-level only.** Refs are shared, so the agent can `git push`, delete `main`, force-reset other branches or move tags. Deny push and branch deletion in the agent's permissions, or run it in a container that mounts only the sandbox dir.
- **External state is shared.** The same DB, Docker volumes, ports and cloud resources are hit from both trees. Give the sandbox its own `.env` with a separate DB or schema, different ports.
- **Secrets travel with `.env`.** Hand the agent scoped or dummy credentials.
- **Untracked files don't come along.** Recreate `.venv`, copy config, and re-run code generation in the new tree.

### Root: workspace

```toml
# pyproject.toml
[project]
name = "credit-risk-mlops"
dependencies = ["simulator", "nbformat"]

[tool.uv.sources]
simulator = { workspace = true }

[tool.uv.workspace]
members = ["simulator"]

[project.optional-dependencies]
dev = ["pytest>=8.0"]
```

A workspace member must use `{ workspace = true }` in sources, not a path. Members are auto-discovered — no `path` needed.

### simulator: standalone project

```toml
# simulator/pyproject.toml
[project]
name = "simulator"
version = "0.1.0"
dependencies = ["numpy>=2.0", "polars>=1.0", "scipy>=1.14", "scikit-learn>=1.6"]

[project.optional-dependencies]
sinks = ["sqlalchemy>=2.0", "psycopg2-binary>=2.9", "boto3>=1.36", "kafka-python>=2.0"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]
force-include = { "src" = "simulator" }   # src/*.py → simulator package
```

The src-layout uses `force-include` so `simulator/src/*.py` installs as the `simulator` package (not `src`). The `sinks` extra adds db/s3/kafka deps only when needed.

### Commands

```bash
uv sync --extra dev                  # root workspace + test deps
uv run pytest tests/ -q              # 11 tests (simulator regression)
uv run python -m simulator           # run generator (output to output/)
uv run --package simulator pytest    # test only the simulator member
uv sync --project simulator          # standalone (no root deps)
```

## The shared library pattern (when you need it)

Currently this project has no shared lib — `simulator` is the only component. If you later add a `serving/` component that needs shared config or feature code:

```
libs/
└── common/
    ├── pyproject.toml
    └── src/common/
        ├── __init__.py
        ├── config.py
        └── features.py

simulator/
    └── pyproject.toml           common = { path = "../../libs/common", editable = true }

serving/
    └── pyproject.toml           common = { path = "../../libs/common", editable = true }
```

### The shared library rules

It **must** declare a `[build-system]`. Without one, uv treats it as a non-package and won't install it into consumers.

```toml
# libs/common/pyproject.toml
[project]
name = "common"
version = "0.1.0"
requires-python = ">=3.13"
dependencies = ["pydantic>=2"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

### A consumer

```toml
# simulator/pyproject.toml (if it consumed common)
dependencies = ["common", "numpy", ...]

[tool.uv.sources]
common = { path = "../../libs/common", editable = true }
```

Or you can let uv write both lines:

```bash
uv add --directory simulator --editable ../../libs/common
```

### Keep shared lib dependencies minimal

- Prefer the stdlib and pure Python.
- Use loose lower bounds (`pydantic>=2`), no upper pins.
- Never put torch, sqlalchemy or cloud SDKs in core `dependencies`.

### Push heavy deps into extras

```toml
# libs/common/pyproject.toml
dependencies = ["pydantic>=2"]

[project.optional-dependencies]
ml = ["torch>=2.2", "numpy>=1.26"]
db = ["sqlalchemy>=2", "psycopg[binary]>=3"]
```

```toml
# simulator/pyproject.toml
dependencies = ["common[db]"]
```

### Lazy-import optional deps

```python
# libs/common/src/common/features.py
def to_tensor(rows: list[list[float]]):
    try:
        import torch
    except ImportError as e:
        raise ImportError("to_tensor needs common[ml]") from e
    return torch.tensor(rows)
```

## Workspace vs independent locks

This project uses a **workspace** (currently one member: `simulator`), meaning one `uv.lock` for the whole repo. This is the right choice when all components should agree on versions.

| | Independent projects + path sources | uv workspace |
|---|---|---|
| Lockfiles | one per component | one `uv.lock` at the root |
| Venv | one per component | one shared `.venv` at the root |
| Version conflicts between components | allowed | impossible: one resolution |
| Shared-lib breakage | found per consumer at `uv lock` | found once, for everyone |
| Bumping a shared dependency | re-lock N projects | re-lock once |
| Best for | ML vs web stacks, legacy pins | services on the same core stack |

If you later add a component with a genuinely divergent stack (e.g. `serving/` with torch 2.6 when `simulator` pins numpy 2.0 which conflicts), exclude it from the workspace:

```toml
[tool.uv.workspace]
members = ["simulator", "libs/*"]
exclude = ["serving"]
```

That component gets its own `pyproject.toml`, `uv.lock` and `.venv`, and pulls shared code through a path source.

## Build backends

The safe default for pure-Python packages in a uv repo is **`uv_build`**, with **hatchling** as the fallback whenever you need hooks or dynamic metadata. Use setuptools only for legacy code, and pick a compiled-extension backend (maturin, scikit-build-core, meson-python) only when you ship native code.

### What a backend is, and when you need one

PEP 517 splits packaging into a **frontend** (uv, pip, `python -m build`) and a **backend** (hatchling, setuptools…). The frontend reads `[build-system]`, installs the backend into an isolated env, and asks it to produce a wheel, an sdist, or an editable install.

```toml
[build-system]
requires = ["<backend package>"]
build-backend = "<module path>"
```

A backend is needed when the project must be **installed as a package**: shared libs, anything path-depended on, anything published, or anything with `[project.scripts]` entry points.

You don't need one for a leaf application you only run (a script run with `uv run`, notebooks, services that nothing imports). Omit `[build-system]`, or set `[tool.uv] package = false`.

### Common backends

| Backend | When to use |
|---|---|
| **uv_build** | Pure-Python packages in uv projects; fastest, strictest. Expects `src/<normalized_name>/__init__.py` |
| **hatchling** | General-purpose pure Python; supports hooks, dynamic version, `force-include` for nonstandard layouts. Used by `simulator/` |
| **setuptools** | Legacy projects with `setup.py`, simple C extensions |
| **maturin** | Rust extensions (PyO3) |
| **scikit-build-core** | C++/CUDA via CMake + nanobind/pybind11 |
| **meson-python** | Fortran, matching numpy/scipy tooling |

### Which one for this project

| Component | Backend | Reason |
|---|---|---|
| `simulator` | hatchling | Needs `force-include` to map `src/*.py` → `simulator` package |
| Root workspace | none (`package = false` implicitly) | Not imported by anything |
| `libs/common` (future) | uv_build | Pure Python, src layout, no hooks needed |

### uv_build specifics

```toml
[build-system]
requires = ["uv_build>=0.12,<0.13"]
build-backend = "uv_build"
```

- Expects `src/<normalized_name>/__init__.py`. For flat layouts, set `[tool.uv.build-backend] module-name = "..."` or `module-root = ""`.
- Pure Python only, no build hooks, no dynamic metadata.
- `uv init --lib` writes it for you.

### hatchling specifics

```toml
[build-system]
requires = ["hatchling", "hatch-vcs"]
build-backend = "hatchling.build"

[project]
name = "common"
dynamic = ["version"]

[tool.hatch.version]
version = "vcs"                    # version from git tag

[tool.hatch.build.targets.wheel]
packages = ["src/common"]
```

Auto-detects both src and flat layouts. Custom build steps go in `hatch_build.py`.

## Cheat sheet

```bash
# --- worktree sandbox ---
git worktree add -b agent/x ../credit-risk-agent main
cd ../credit-risk-agent
uv sync --extra dev
# hack, commit, push
cd ../credit-risk-mlops
git diff main...agent/x
git merge --squash agent/x && git commit -m "feature: ..."
git worktree remove --force ../credit-risk-agent
git branch -D agent/x

# --- simulator standalone ---
uv sync --project simulator
uv run  --project simulator python -m simulator

# --- workspace ---
uv sync --extra dev                     # root workspace + test deps
uv run pytest tests/ -q                 # 11 tests
uv run python -m simulator              # generate data
uv run --package simulator pytest       # test only simulator member

# --- add a shared lib (future) ---
mkdir -p libs/common/src/common
uv init --lib libs/common
uv add --directory simulator --editable ../../libs/common

# --- lock after dep changes ---
uv lock --project simulator             # if simulator's deps changed
uv sync --extra dev --locked            # CI: fail if stale
for p in libs/*/ simulator; do uv lock --project "$p"; done
```

### Rules of thumb

- One agent per worktree and branch; scoped `.env`; no push permission.
- The shared lib has a `[build-system]`, minimal core deps, heavy deps in extras, and lazy imports.
- Changing shared deps means re-locking every consumer; CI runs `--locked`.
- Use a workspace for one shared stack, independent locks for divergent stacks, and both where needed.

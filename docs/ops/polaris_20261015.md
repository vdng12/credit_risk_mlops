## Concepts — Iceberg REST catalog & Polaris server

### The Iceberg catalog model

Iceberg organizes metadata as a three-level hierarchy:

```
Catalog
  └── Namespace      (a folder / grouping of tables, like a schema)
        └── Table    (the actual dataset, with schema + history)
        └── View     (a logical query/transformation, optional)
```

- **Catalog** — top-level container that stores the location of table metadata
  and the pointer to each table's current `metadata.json`.
- **Namespace** — grouping of tables (schema/database equivalent).
- **Table** — partitioned Parquet data + a chain of `metadata.json`/manifest
  files. Every write produces a new immutable snapshot (time travel).

### What the REST catalog server does

Engines (Spark, Trino, DuckDB, PyIceberg) don't read Iceberg metadata directly
from storage. They talk to a **catalog** via the **Iceberg REST API spec**, and
the catalog tells them *where* the metadata lives and *what* the current snapshot
is. Polaris is the server that implements this spec:

```
Engine ──HTTP (Iceberg REST spec)──▶ Polaris server ──metadata ops──▶ Object store (S3)
```

Responsibilities:

- Table discovery: `listNamespace`, `listTables`, `loadTable`
- Schema evolution: `createTable`, `commit` (with optimistic-concurrency checks)
- Snapshot / history: `createTable`, `registerTable`, time travel
- Branching & tagging (Iceberg v3 features exposed over REST)

### Polaris server concepts

| Concept | Meaning | In our setup |
|---|---|---|
| **Realm** | An isolated security/policy boundary | `POLARIS` (the default realm) |
| **Principal** | A user/service account identity | `root` |
| **Principal role** | Capabilities attached to a principal | `PRINCIPAL_ROLE:ALL` (catalog admin) |
| **Credential** | OAuth client_id + secret for a principal | `root` / `s3cr3t` |
| **Token broker** | OAuth2 endpoint that exchanges creds → JWT | `/api/catalog/v1/oauth/tokens` |
| **Catalog** | A named Iceberg catalog registered in Polaris | *(to be created)* |
| **Storage config** | Where + how table files are stored (S3 endpoint, keys) | SeaweedFS `http://seaweedfs:8333` |
| **Metastore** | Where Polaris persists its own realm/catalog/principal data | in-memory (dev) |

### Request path shape

Polaris exposes the standard Iceberg REST API with realm routing:

```
http://<host>:8181/api/catalog/v1/{optional-realm-prefix}/catalogs
http://<host>:8181/api/catalog/v1/{optional-realm-prefix}/catalogs/{catalog}/namespaces
http://<host>:8181/api/catalog/v1/{catalog}/namespaces/{namespace}/tables
```

- The `/config` endpoint and `/oauth/tokens` are realm-agnostic.
- Without a `realm` header, requests default to the `POLARIS` realm
  (the `polaris.realm-context.require-header` warning below is about tightening
  this for multi-realm deployments).

## 1. Final service config (`docker-compose.yml`)

```yaml
polaris:
  image: apache/polaris:latest
  container_name: polaris
  environment:
    POLARIS_BOOTSTRAP_CREDENTIALS: "POLARIS,root,s3cr3t"
    AWS_ACCESS_KEY_ID: ${S3_ACCESS_KEY:-seaweedfs}
    AWS_SECRET_ACCESS_KEY: ${S3_SECRET_KEY:-seaweedfs123}
    AWS_REGION: us-east-1
    AWS_ENDPOINT_URL_S3: http://seaweedfs:8333
  ports:
    - "8181:8181"   # REST API
    - "8182:8182"   # management / health
  networks:
    - risk-net
  restart: unless-stopped
  healthcheck:
    test:
      [
        "CMD-SHELL",
        "curl -sf http://localhost:8182/q/health/ready | grep -q UP || exit 1",
      ]
    interval: 15s
    timeout: 5s
    retries: 5
    start_period: 60s
```

Credentials: realm `POLARIS`, client ID `root`, secret `s3cr3t`.

### Line-by-line rationale

| Setting | Why |
|---|---|
| `image: apache/polaris:latest` | Official Apache image (1.6.0) |
| `POLARIS_BOOTSTRAP_CREDENTIALS` | Format `realm,clientId,clientSecret`; realm must be `POLARIS` |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | AWS SDK v2 env vars — read by Polaris S3FileIO |
| `AWS_REGION` | Required by SDK; arbitrary value is fine for SeaweedFS |
| `AWS_ENDPOINT_URL_S3` | SDK v2 endpoint override → routes to `seaweedfs:8333` |
| `8181` | Iceberg REST catalog API |
| `8182` | Quarkus management (health/metrics) |
| `curl -sf ... /q/health/ready` | Quarkus readiness probe; `-f` fails on HTTP error |

## 4. Component architecture

```
                 :8181 (Iceberg REST spec)
   clients ───▶ REST API ───▶ Iceberg metadata ops
    Spark/          │
    Trino/         ├──▶ Token broker (OAuth2/JWT, RS256)
    DuckDB/        ├──▶ Realm store (POLARIS realm, principals, roles)
    PyIceberg      ├──▶ Metastore (in-memory | Postgres | Mongo)
                   └──▶ S3FileIO (AWS SDK v2) ──▶ SeaweedFS :8333
                 :8182 (Quarkus management)
                   └──▶ /q/health/ready, metrics, cache-coherency
```

Runtime facts:

- Boot time: ~3.5–4.3 s
- Heap: `-XX:MaxRAMPercentage=80.0`, `-XX:+UseParallelGC`
- Caffeine persistence cache: ~6.5 GB capacity
- Cache invalidation endpoint: `/polaris-management/cache-coherency`

## 6. Gotchas

1. **Wrong realm name → silent random creds.**
   Symptom: `realm: POLARIS root principal credentials: 615aee...` printed.
   Fix: `POLARIS,root,s3cr3t`.

2. **`wget` missing.**
   Symptom: healthcheck never passed; `sh: wget: command not found`.
   Fix: `curl -sf`.

3. **`POLARIS_S3_*` env guesses were unverified.**
   Some may be inert smallrye-config keys. Switched to SDK-standard
   `AWS_REGION` + `AWS_ENDPOINT_URL_S3` (verified via bundled SDK jars).

4. **In-memory metastore = tests only.**
   Symptom: readiness warning `'polaris.persistence.type'`. Fix before K8s.

5. **Generated (non-persistent) RSA keys.**
   Symptom: warnings for missing `public-key-file` / `private-key-file`.
   For K8s: mount a key pair.

6. **Lenient realm header mapping.**
   Symptom: `'polaris.realm-context.require-header'` warning — requests without
   a realm header default to `POLARIS`. Set `require-header=true` for multi-realm.

7. **`docker compose down` teardown accident** (compose-level, not Polaris):
   passing a service name tore down the whole project; recovered because named
   volumes persist without `-v`.

## 1. uv workspace restructure

The simulator was a standalone uv project (own `uv.lock`, own `.venv`,
hatchling `force-include` shim). It is now a clean workspace member.

| Item | Before | After |
|---|---|---|
| Layout | `simulator/src/*.py` flat | `simulator/src/simulator/*.py` (standard src layout) |
| Build backend | hatchling + `force-include` | `uv_build` (auto-detects src layout) |
| Locks | root + `simulator/uv.lock` | single root `uv.lock` |
| Root deps | `[project.optional-dependencies]` dev/eval | `[dependency-groups]` dev/eval, `default-groups = ["dev"]` |
| Entry point | `python -m simulator` only | `[project.scripts] simulator = "simulator.__main__:main"` |
| Image | - | `simulator/Dockerfile` (multi-stage uv build) + `.dockerignore` + `infra/k8s/simulator/manifest.yaml` CronJob |

The console-script entry point means `uv run simulator ...` equals
`python -m simulator ...`, and images can use `ENTRYPOINT ["simulator"]`. The
Dockerfile syncs with `--no-install-workspace` (layer 1) then
`--package simulator --all-extras` (layer 2) to install the member including
the `sinks` extra.

Verified: `uv sync --locked`, 11/11 tests, wheel built with the correct
`simulator/` package contents, scratch sync produced `.venv/bin/simulator`.

## 2. Sinks made consistent with design (was: dead code + silent failures)

Reading the routing code against AGENTS.md exposed a large gap:

- `SinkManager.to_postgres()` existed but nothing ever called it.
- `__init__.py` advertised a `MonthBatch.to_postgres(engine)/to_seaweedfs()`
  API that did not exist (docstring fixed).
- S3 and Kafka failures were silently swallowed (`except Exception: pass`),
  so earlier "validation" actually tested that nothing reached the cluster.
- `postgresql://` DSNs broke under SQLAlchemy 2.1 (defaults to psycopg3,
  only psycopg2-binary installed) - fixed by pinning `postgresql+psycopg2`.
- kafka-python 3.x `SerializeWrapper` call-contract churn.
- `to_postgres` now projects the frame onto the target table's columns (the
  OLTP schema is the contract - e.g. `loan_applications` carries only
  pre-decision fields; decisions/rejections live in `application_decisions`).

New `SinkConfig` is 12-factor: `SIM_POSTGRES_DSN`, `SIM_S3_ENDPOINT`,
`SIM_S3_ACCESS_KEY`, `SIM_S3_SECRET_KEY`, `SIM_S3_BUCKET`, `SIM_OUTPUT_DIR`,
plus per-sink toggles `enable_s3` / `enable_postgres` (CLI: `--no-s3`,
`--no-postgres`). Default output dir changed from `data/generated` to
**`outputs/generated`** (gitignored and dockerignored).

## 3. CDC-only streaming (the deploy-topology decision)

Discovered during validation that the deployed "hot lane" is not what the
docs described:

- Redpanda topics (`lending.public.*`) are produced by the Debezium CDC
  connector watching postgres-source, not by any direct producer.
- The generator's direct Kafka writes created parallel topics
  (`loan_applications` vs `lending.public.loan_applications`) the DE pipeline
  never consumes.

**Decision:** Kafka is a re-publication of Postgres OLTP writes. The
generator now writes everything COLD-first and never touches Kafka:

| destination | entities |
|---|---|
| local parquet write-through (`outputs/generated/<run>/`) | all 9 |
| Postgres `lending_db` (OLTP, streamed by Debezium CDC) | clients, loan_applications, card_authorizations, application_decisions, payments |
| Postgres `lending_db` (gold layer, no CDC) | application_master |
| SeaweedFS S3 `risk-data` | clients, application_decisions, pos_balances, card_balances, bureau |

Removed: `to_kafka`, kafka-brokers/topics config, `enable_kafka`,
`--no-kafka`, and the `kafka-python` dependency (lock re-resolved).

Validation (E2E against the live stack, via `kubectl port-forward` because
host ports were broken - see section 4): all 6 PG tables populated, 5 S3
entities as parquet, Debezium envelopes confirmed with `op=c` and full
simulated rows.

## 4. k3d rebuild and host-port recovery (two stacked root causes)

**What was broken:** every host port (5432, 8333, 9092, 5000, ...) refused
connections; `k3d cluster list` was empty; a leftover control-plane container
from a hand-built cluster held the state.

**Cause A - k3d v5.9 no longer provisions an in-cluster gateway for custom
`-p` ports.** Its serverlb routes `host:8333` to `server-0:8333`, but nothing
listens on the server node (no gateway/LoadBalancer svc, no NodePorts), so
connections died. This is why the whole session ran on `kubectl port-forward`.

**Fix A:** all 7 service manifests use `type: NodePort` with `nodePort` equal
to the documented host mapping, and k3d-up.sh gained
`--k3s-arg "--kube-apiserver-arg=service-node-port-range=1-65535@server:0"`
(low nodePorts allowed). Important: this only works if the cluster is
recreated with the patched `ops/k8s/k3d-up.sh` - an earlier attempt ran the
original script (the edit lived in another worktree), and the API kept
rejecting `nodePort: 5432` as out of range.

**Cause B - k3s RBAC crash-loop (17 restarts).** Cloud-controller-manager
died on `configmaps "extension-apiserver-authentication" is forbidden`, and
k3s shut down in a loop. Traced to stale k3d runtime state across a confused
delete/rollback sequence; a fully clean `k3d cluster delete risk-cluster`
(rechecking leftover containers/volumes) followed by a fresh create booted
stable (`Restarts: 0`).

**Post-rebuild chores (not yet automated):**
- `docker build -t risk-mlflow:latest -f infra/k8s/mlflow/Dockerfile .` plus
  `k3d image import -c risk-cluster risk-mlflow:latest` (the custom image is
  not in the registry).
- `bash ops/debezium/register-connector.sh` (the connector lives in Connect
  runtime state, not the manifests; it covers `public.clients,
  loan_applications, application_decisions, payments, card_authorizations` -
  `application_master` is deliberately not CDC'd).
- Recreate the S3 bucket: `risk-data` is not auto-created by SeaweedFS.
- Seed: the init SQL (`infra/postgres/init/01-init-schema.sql`, embedded in
  the postgres-source manifest) creates schema only, zero rows - the old
  "20 customers" seed is gone, and AGENTS.md still says otherwise.
